# Git: Контрольные вопросы для самопроверки

> [!abstract] О материале
> Конспект-шпаргалка с ответами на ключевые концептуальные вопросы по Git: архитектура, объекты, ветвление, разрешение конфликтов и безопасная отмена изменений. Подходит для подготовки к собеседованиям и повторения базы.

---

### 1. Что такое система контроля версий и для чего она используется?
**Система контроля версий (VCS)** — это программное обеспечение для отслеживания и фиксации изменений в файлах проекта во времени.
- Позволяет откатываться к прошлым состояниям и ревизиям.
- Сохраняет историю: автор, время, суть изменений.
- Делает возможной параллельную работу нескольких разработчиков над одним проектом без затирания кода.

---

### 2. Для чего используется Git?
**Git** — это распределённая система контроля версий (DVCS).
- Локальная фиксация состояний проекта без необходимости постоянного подключения к сети.
- Быстрое и легковесное ветвление для разработки изолированных фич и багфиксов.
- Эффективное слияние веток и распределённая синхронизация между участниками команды.

---

### 3. Чем Git отличается от GitHub?
| Характеристика | Git | GitHub |
| :--- | :--- | :--- |
| **Тип** | Консольный инструмент / CLI | Облачный сервис / Веб-платформа |
| **Локация** | Локальная машина | Удалённые серверы Microsoft |
| **Функции** | Управление версиями, ветки, слияния | Хостинг репозиториев, PR / Code Review, Issues, CI/CD, Wiki |
| **Интернет** | Полностью автономен | Требует подключения к сети |

---

### 4. Что такое Git-репозиторий?
**Репозиторий** — это единое хранилище проекта. Состоит из:
1. **Рабочего каталога** (рабочих файлов проекта, которые видит пользователь).
2. **Служебной базы данных (`.git`)**, в которой хранятся объекты (коммиты, деревья, блобы), история изменений, ветки и конфигурация.

---

### 5. Для чего используется каталог `.git`?
Каталог `.git` — это скрытое «сердце» репозитория. В нём хранятся:
- **Объекты (`objects/`)**: сжатое содержимое файлов (blobs), структура папок (trees), коммиты (commits) и теги (annotated tags).
- **Ссылки (`refs/`)**: указатели на ветки (`heads`), теги (`tags`) и удалённые ветки (`remotes`).
- **`HEAD`**: файл, указывающий на текущую активную ветку или конкретный коммит.
- **`index`**: файл состояния буферной зоны (Staging Area).
- **`config`**: локальные настройки репозитория.

> [!warning] Внимание
> Удаление каталога `.git` превращает проект в обычную папку с файлами и безвозвратно уничтожает всю историю версий.

---

### 6. Что такое рабочий каталог (Working Directory)?
Это файловая директория на диске, содержащая файлы проекта в распакованном виде. Именно здесь ведётся реальная работа: редактирование кода, создание и удаление файлов.

---

### 7. Что такое индекс Git (Staging Area / Cache)?
**Индекс** — промежуточная область между рабочим каталогом и постоянной историей коммитов. Это подготовленный снимок (бинарное состояние), отражающий, какие именно изменения войдут в следующий коммит.

---

### 8. Что делает команда `git add`?
Переносит изменения из рабочей директории в **индекс (Staging Area)**:
- Вычисляет хеши для изменённых файлов и создаёт соответствующие blob-объекты в `.git/objects`.
- Обновляет файл `.git/index`.
- Готовит файлы к фиксации через `git commit`.

---

### 9. Что такое коммит?
**Коммит** — неизменяемый криптографический слепок (снапшот) индекса в определённый момент времени.  
Коммит содержит:
- Ссылку на дерево каталогов (Tree object).
- Ссылку на родительский коммит (или двух родителей при merge).
- Метаданные: автор, коммитер, дата/время, сообщение коммита.
- Уникальный SHA-хеш (SHA-1 или SHA-256).

---

### 10. Почему рекомендуется создавать небольшие логически завершённые коммиты?
- **Понятный Code Review**: коллегам проще и быстрее проверять атомарные правки.
- **Точечный откат**: команду `git revert` можно применить к изолированному коммиту без побочных эффектов.
- **Отладка с `git bisect`**: бинарный поиск бага точно укажет на 5 строк ошибки, а не на коммит размером в 50 файлов.
- **Меньше конфликтов**: снижается риск пересечения логики с параллельными ветками.

---

### 11. Что показывает команда `git status`?
Информационную сводку текущего состояния:
1. Текущая активная ветка и её статус относительно upstream (опережает / отстаёт).
2. Изменения в индексе, готовые к коммиту (*Changes to be committed*).
3. Изменения в файлах, не добавленные в индекс (*Changes not staged for commit*).
4. Новые неотслеживаемые файлы (*Untracked files*).

---

### 12. Для чего используется `git diff`?
Для сравнения содержимого и просмотра диффов:
- `git diff` — разница между рабочим каталогом и индексом.
- `git diff --staged` (или `--cached`) — разница между индексом и коммитом `HEAD`.
- `git diff HEAD` — разница между рабочим каталогом и `HEAD`.
- `git diff branch1..branch2` — сравнение двух веток или коммитов.

---

### 13. Что представляет собой ветка в Git?
Ветка — это всего лишь **легковесный текстовый указатель (ссылка)** на конкретный коммит (файл в `.git/refs/heads/<name>`, хранящий 40-символьный хеш). При создании нового коммита указатель автоматически сдвигается на вновь созданный коммит.

---

### 14. Для чего используются ветки?
- **Изоляция контекста**: параллельная разработка разных фич без взаимного влияния.
- **Стабильность релиза**: ветка `main` / `master` всегда остаётся в рабочем состоянии, готовом к деплою.
- **Эксперименты**: возможность проверить гипотезу и легко удалить ветку, если идея оказалась неудачной.

---

### 15. Что происходит при выполнении `git merge`?
Происходит интеграция изменений из целевой ветки в текущую:
1. **Fast-forward (перемотка)**: если в текущей ветке новых коммитов не было, указатель ветки просто сдвигается вперёд к концу вливаемой ветки. Новых коммитов не создаётся.
2. **3-way merge (трёхстороннее слияние)**: если ветки разошлись, Git находит их общего предка (merge base) и создаёт новый специальный **merge-коммит**, имеющий двух родителей.

---

### 16. Что такое конфликт слияния (Merge Conflict)?
Ситуация, возникающая при слиянии, когда в обеих ветках были изменены одни и те же строки в одном и том же файле (или один разработчик удалил файл, а другой его модифицировал), и Git не может решить автоматически, какой вариант оставить.

---

### 17. Почему Git не всегда может автоматически разрешить конфликт?
Git оперирует текстовыми строками, а не синтаксисом и семантикой языка. Он не знает бизнес-логику и архитектуру приложения. Автоматический выбор одного из вариантов мог бы привести к скрытым багам или удалению критического кода, поэтому принятие решения возлагается на человека.

---

### 18. В чём разница между `git restore` и `git revert`?
- **`git restore`**: работает с локальным незафиксированным состоянием. Сбрасывает правки в рабочей директории или убирает файл из индекса (`--staged`). История коммитов не затрагивается.
- **`git revert`**: создаёт **новый публичный коммит**, вносящий строго противоположные изменения по отношению к указанному коммиту в истории.

---

### 19. Почему отмена изменений в Git может быть сложной операцией?
- **Разные зоны хранения**: отмена зависит от того, где находится код (рабочая копия, индекс, локальный коммит или удалённый репозиторий).
- **Риск безвозвратной потери**: незакоммиченные правки, стёртые через `git restore` или `git reset --hard`, невозможно восстановить даже через `reflog`.
- **Влияние на команду**: отмена уже опубликованных коммитов требует деликатности, чтобы не нарушить историю у коллег.

---

### 20. В принципиальная разница между `git revert` и `git reset`?
> [!tip] Главное отличие
> `git revert` сохраняет историю неизменной, двигаясь вперёд. `git reset` переписывает историю, отматывая время назад.

- **`git reset`**: перемещает указатель текущей ветки назад во времени.
  - `--soft`: коммиты убираются, изменения остаются в индексе.
  - `--mixed` (дефолт): коммиты убираются, изменения остаются в рабочей директории.
  - `--hard`: коммиты и файлы стираются начисто до состояния целевого коммита.
  *Применять только для локальных коммитов!*
- **`git revert`**: безопасный откат коммита. Не удаляет ничего из истории, создавая новый коммит-«антидот». Идеален для общих публичных веток.

---

### 21. Почему изменение уже опубликованной истории может создать проблемы при командной разработке?
Если переписать историю локально (`git commit --amend`, `git rebase`, `git reset`) и протолкнуть её через `git push --force`:
- Изменятся SHA-хеши коммитов.
- У коллег, которые уже сделали `git pull`, локальная ветка разойдётся с удалённой.
- При следующем слиянии или pull возникнут дублирующиеся коммиты («фантомная» история) и массовые ложные конфликты слияния.

---

### 22. Может ли Git работать без GitHub и подключения к Интернету?
**Да, абсолютно.**  
Git — это **полностью децентрализованная (распределённая)** система. Каждый локальный репозиторий содержит полную автономную базу данных истории. Без интернета доступны:
- Создание веток и переключение между ними.
- Коммиты, просмотр логов и диффов.
- Слияния и разрешение конфликтов.
- Передача патчей и коммитов напрямую по локальной сети или через флешку (`git bundle` / SSH).
